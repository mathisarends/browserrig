# SMT110 imports/excess-module-imports

A module imports more project modules than its policy allows.

- **Category:** imports
- **Activation:** policy — style or a package override sets max_module_imports, including zero.
- **Severity when active:** hint

## Why

Many independent project dependencies can signal that a module coordinates too many responsibilities. Unlike SMT108, this review counts distinct direct target modules across every project root package, without requiring a contract on each target package. Repeated imports and multiple symbols from one module count once. Facade re-exports count at the facade path used by the caller, not at their defining modules. Standard-library and third-party imports never count; TYPE_CHECKING imports follow the existing architecture.import_graph.type_checking policy. Initializers and declared composition roots are exempt by default. This is a design hint, not proof of excessive coupling; reducing imports alone does not simplify a design.

## Bad

```python
# app/client.py
from app.users.read import Read
from app.users.write import Write
from app.billing.pay import Pay
```

## Good

```python
# app/client.py, after deliberate facade review
from app.users import Read, Write
from app.billing import Pay
```

## How to fix

Split a cohesive responsibility into its own module or depend on deliberate package facades. Review import cycles and initializer side effects before adding re-exports. No automatic rewrite is performed. Set max_module_imports under style or in a style override to enable this opt-in hint for that scope (zero is supported). Selecting the rule in rules or with --select uses a limit of 20. module_import_exemptions defaults to [facades, composition_root]; [] checks both.

## Config

- `style.max_module_imports`
- `style.module_import_exemptions`
- `style.overrides`
- `rules`
- `architecture.composition_root`
- `architecture.import_graph.type_checking`

Explain it in the terminal with `smelt explain SMT110`.
