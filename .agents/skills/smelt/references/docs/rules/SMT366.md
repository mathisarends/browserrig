# SMT366 comprehension-in-call-argument

An eager comprehension is passed directly as a call argument.

- **Category:** structure
- **Activation:** explicit — Enable by rule setting or --select.
- **Severity when active:** hint

## Why

Naming collection transformations before passing them on separates calculation from object construction or consumption. This opt-in syntax review reports list, set and dict comprehensions used as direct positional or named keyword arguments in production code, once per argument. It applies to any call without inferring constructors or runtime types. Simple mappings are included even when SMT363 accepts their internal logic. Named collections, ordinary calls and attribute reads, generator expressions, starred arguments and comprehensions nested inside another argument expression are outside scope. Calls within lambdas, comprehensions, conditional expressions, boolean operators, chained comparisons, assert messages and while conditions are skipped because extraction can change when or how often they run. Tests are excluded.

## Bad

```python
def to_response(result):
    return Response(users=[to_user(user) for user in result.users])
```

## Good

```python
def to_response(result):
    users = [to_user(user) for user in result.users]
    return Response(users=users)
```

## How to fix

Assign the comprehension to a local variable before the call and pass that variable. A named keyword supplies a suggested variable name. Preserve the callable lookup, argument evaluation order, guards and suspension points: moving an argument before the call can evaluate it before earlier arguments or the callable itself. Do not eagerly materialize generator expressions. No automatic rewrite is performed. Enable rules: {comprehension-in-call-argument: hint} or select SMT366. Package overrides and reasoned inline suppressions are supported.
