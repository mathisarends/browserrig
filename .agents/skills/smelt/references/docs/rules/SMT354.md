# SMT354 prefer-domain-exception

Production code raises a builtin exception instead of the project hierarchy.

- **Category:** structure
- **Activation:** policy — A package contract sets errors, including {}.
- **Severity when active:** warning

## Why

A project exception hierarchy lets callers tell a domain failure apart from a programming error. Code that keeps raising ValueError or RuntimeError for domain failures, or converts every error into one, forces callers to catch broad builtins and guess what went wrong. A package contract names the project base, e.g. errors: {base: app.errors.AppError}, and production code in the package that raises a builtin exception class, with or without arguments and with or without from, is reported. NotImplementedError, StopIteration, StopAsyncIteration, GeneratorExit, KeyboardInterrupt and SystemExit are always allowed, and errors.allow adds more, e.g. [TypeError]. Bare re-raises, raising caught or project exceptions, names that shadow a builtin, raises in protocol dunder methods such as __getattr__ or __getitem__, and pydantic validators, which must raise ValueError or AssertionError, are not reported. Tests are not checked.

## Bad

```python
try:
    return self._read(path)
except Exception as error:  # surface unreadable files
    raise ValueError(f"Could not read {path.name}") from error
```

## Good

```python
from app.errors import ReadError

try:
    return self._read(path)
except Exception as error:  # surface unreadable files
    raise ReadError(f"Could not read {path.name}") from error
```

## How to fix

Raise a subclass of the configured base that names the failure, and let callers catch that subclass. When callers rely on a builtin, for example TypeError for wrong argument types, add it to errors.allow, or set errors: {} in a nested package that deliberately raises builtins. No automatic rewrite is performed. Enable it with a package contract, e.g. structure.contracts.<name>: {match: app, errors: {base: app.errors.AppError}}.
